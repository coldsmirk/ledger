# Architecture

Contributor-facing: how the package is built, the internal pipelines, and the invariants that must survive changes. The user-facing contracts these implement live in the guides; the design rationale is [DESIGN.md](DESIGN.md).

## Load-bearing internals

**Option partition with compile-time exhaustiveness.** Sugar mode splits props into behavior options vs presentation by the `OPTION_KEYS` list; `AssertNever<MissingOptionKeys>` makes *forgetting to list a new `UseDataTableOptions` key* a type error at the `Set` construction site. Add an option → add it to `OPTION_KEYS` or the build fails.

**One erasure boundary.** `context.ts` erases `TData` for table-wide plumbing (styles getter, labels, row handlers, the active-row switch and its setter, the column-filter set notification), and since the v9 migration the internal render layer below it is `any`-bound as well — TanStack v9's `in out` (invariant) generics make cross-instantiation unification of generic internals a fight with no type-safety payoff, so the erasure happens once at `DataTableCore` and the public surface stays strongly typed. Any new cast belongs *at that boundary*, not scattered through the tree.

**Ledger never lets a render nobody saw decide anything.** TanStack v9's `useTable` calls `table_setOptions` *during render*, so the one shared core instance carries whatever pass ran last — including a pass React threw away, which is what happens whenever a transition renders and a sibling suspends. Everything the core derives follows: `getRow` and the row models, `getAllLeafColumns` and the `columnDef` on each, and `options.meta.ledger`. The wrapper `useTable` returns is safe — its `options` is that render's own object — but its *methods* delegate to the core, so reaching through one at event time reaches the last render rather than the last commit.

**The table instance is not in the context, and no ref holds it.** Everything under `<DataTable>` that is not the root can render without the root rendering with it — a filter popover redrawing from its own state, a row the virtualizer puts back, a cell editor answering a keystroke. A context field that read the instance through a render-written ref would hand those renders whatever pass wrote it last. So the context carries the few table-wide facts the tree needs as fields of their own, each stable enough that naming them individually is what keeps the context value itself stable while the v9 wrapper changes identity on every state tick. What is not stable does not go there: `renderDetailPanel` is normally written inline, so a detail row takes it as a **prop** from the body's own render instead — the render that put that row on screen.

`use-committed-table.ts` is the answer for editing: a snapshot taken in an **insertion effect** (the commit phase, before every layout effect) of the rows, the leaf columns and their definitions, the visible order, and the table-level gate — the switch and the live mode's commit handler together. Two rules follow, and both are load-bearing:

- **Event time reads the commit.** Every *editing* decision — the gate, `previousValue`, `validate`, where F2 enters, which column Tab moves to, whether a row is even there — resolves from the snapshot. "There" has two meanings and the snapshot keeps them apart: `row` reaches back to the pre-paginated and core models, because a session may legitimately name a row that is filtered out or has not arrived, while `onScreen` answers only for the rows that render — which is what F2 needs, since an editor nobody can see is not an entry point. Values go through the *committed column's* `accessorFn` over the committed `row.original`, never `row.getValue`, which resolves its column through the core. Display order in the snapshot is pinned-aware (`start + center + end`), like everywhere else. And Tab resolves its destination **after** its commit succeeds, never when the key was pressed: an async write leaves the keyboard free, and a real render landing while it is out can hide that column or shut its gate.
- **Render time reads the render.** `canEditCell` in `table-body.tsx` reads the definitions and switches through the cell's own table, which is correct while a render is in progress — that *is* the render being drawn. The value a host hands `drafts.read` follows the same rule but not the same route: it comes from `cellValue(cell)`, this render's column accessor over this row's `original`, **not** `cell.getValue()`. Upstream caches a row's values on the row object and rebuilds that cache only when `data` changes, so a column whose `accessorFn` changed under identical data would go on answering with the one it had before — a plain staleness bug, quite apart from any discarded render.

What this does **not** claim:

- The upstream mutation is untouched, and nothing here fixes it.
- The TanStack `row` / `column` handed to an application in a commit payload are the objects that render resolved, not reconstructions — a `Row` method the application calls itself (`row.getValue`) still goes to the core.
- A `Row` or `Column` method an **application** calls itself still goes to the core. Ledger isolates its own controls, not TanStack's API.

**The active row and the imperative scroll answer from the render on screen.** Arrow keys, `Home`/`End`, the live-region announcement and `scrollToRow` all used to rebuild their row list when the event arrived, which is the shared core's list. They now read one `DisplaySnapshot` built by the render itself — the pinned-aware `top + center + bottom` order, the centre zone the virtualizer indexes, the page's own model that `scrollToIndex` counts through, and the leading data column that names a row to a reader — and reach it through a `useEventCallback` closure, which is mirrored in an insertion effect and is therefore always the snapshot of the render that reached the screen. The arrays are TanStack-memoized, so holding them costs nothing per scroll step, and the work each key does stays where it was: derived at event time, from arrays that cannot change under it. The announcement names the row through that column's own `accessorFn`, for the reason `cellValue` exists. F2 is not part of this — the row it acts on is the active-row slice and where it opens is the editing controller's answer, both already committed.

**Sorting, selection and expansion toggles carry their render with them.** v9 computes half of each toggle *outside* the updater it hands the state setter — the next sort direction and the sort gate, `getCanSelect`/`getCanMultiSelect`, the Shift anchor and the display order it walks, whether a row is currently expanded — and that half reads the shared core, while the updater's own `old` is correctly the committed value. Six probes, each green without a discarded render and red with one, pinned what the disagreement costs: a sort click took its direction from the discarded state (ascending came out descending) and its gate from a discarded `enableSorting` (the click did nothing at all); a selection click lost its gate the same way; a Shift range and a select-all covered the discarded row model instead of the rows on screen; an expander toggle computed against a discarded `expanded` became a silent no-op.

`toggle-fns.ts` is those updater bodies transcribed as pure functions — multi-sort with `maxMultiSortColCount`, the sub-row selection cascade, the range interval, the select-all ancestor walk, the `expanded === true` materialization — reading nothing but structural row properties (`id`, `subRows`, `parentId`) and the rules its caller resolved. `use-row-commands.ts` resolves those rules and the row order **in an insertion effect** and exposes two stable controllers; the sort spec is smaller and rides the render that drew the header, like a `ResizerSpec`. The Shift anchor moved with them: v9 keeps it on the core instance (`_lastSelectedRowId`), which is the one object a discarded render also writes. One restatement is load-bearing: a feature's `getDefaultTableOptions` is merged into the **core's** options, not into the wrapper's, so `isMultiSortEvent` is defaulted at the header rather than read blindly — a consumer override through `tableOptions` still wins.

**Storage and the environment are trust boundaries, and both fail quietly.** `persistState` serializes in the render that produced the state but can never throw out of it: a filter value may be a BigInt, refer to itself, or own a `toJSON` that throws, and any of those would take the table down on a keystroke. An unserializable state cancels the pending write instead — it never leaves the previous payload standing in for the current state — and says so once in dev. Reading back is the mirror: shape guards decide whether a slice can be used at all, and `columnPinning` is additionally repaired to unique-and-disjoint, because the same column pinned twice is drawn twice. `isDev` reads `process.env.NODE_ENV` **unguarded** and catches the failure, which is the only shape that works in all three places at once: Vite substitutes that expression textually in client code (library source served through the `source` condition included), so a `typeof process` guard in front of it silences every dev warning in the browser where developers read them, while treating a missing `process` as development leaves the warning channel alive in a production bundle.

**State reads inside the library go through `table.atoms.<slice>.get()`**, never `table.state`: `.state` exists only on the wrapper `useTable` returns, while a component hosted in a header renderer (the columns panel behind a cog) receives the core instance, and atoms live on both. What they are **not** is a current-tree snapshot: for a controlled slice the atom's read resolves through the shared `table.options.state`, which is the very thing a discarded render rewrites. So atoms are the state *API*, and anything that has to answer for the tree on screen — a pointer session, an editing command — takes its answer from a committed closure or the committed snapshot instead.

**Header, body, and footer are separate tables under one ARIA table.** The header (and, when any column declares a `footer`, the totals region) sits in an `overflow: hidden` viewport outside the body ScrollArea, so the vertical scrollbar spans exactly the rows (never occluded, never bounced by overscroll) and totals stay visible. Three invariants keep the tables pixel-equal: identical Mantine props, identical `<colgroup>`s, and the shared root-level column variables — which requires `table-layout: fixed` on all, always (auto layout would distribute each table independently). Horizontal sync is one assignment — the body's scroll event mirrors `scrollLeft` onto the header and footer viewports in the same frame; native non-passive wheel listeners forward **dominantly horizontal** deltas (`|deltaX| > |deltaY|`, so vertical-leaning wheels keep scrolling the page) from those regions to the body. The body viewport is `overscroll-behavior: none` (inline via `viewportProps`): rubber-band overscroll translates the body past the clamped scroll position the mirrors read, shearing the regions apart for the duration of the bounce. Because the native tables would split the semantics, all are `role="presentation"` and the explicit ARIA table lives on `main` with `row` / `columnheader` / `cell` roles on the parts — keep those roles when adding new row kinds.

**Seam lines at and below the scroller's bottom edge are inset overlays** (EP's inner-wrapper technique): at scroll end the last row's border occupies the viewport's last pixel, so a real border on the next region (frame bottom, footer top, pagination top) stacks into one thick line. The scroller's `::after` owns the bottom seam, the footer separates with its trailing edge only, and the `withTableBorder` frame draws three real sides plus an overlay bottom — all coinciding on the same pixel instead of adding one below. The overlays sit at `z-index: 2` (the pinned-cell tier, which they follow in tree order): anything lower and a scrolling pinned cell's opaque background erases the line in its column's range. Never give a region below the body a leading (`border-block-start`) separator. The ScrollArea scrollbars (the `[data-orientation]` children) get `z-index: 3` — above pinned cells (2), like every native overlay scrollbar — or the covered track stretch is unreachable and the thumb vanishes under a pinned column at the scroll extremes.

**Column geometry is CSS variables, and the numbers come from the width engine.** `use-column-widths.ts` resolves every visible leaf column to exact integer pixels (docs/sizing.md); widths (`--ledger-col-width-<id>`) and pinned offsets (`--ledger-col-start/after-<id>`, summed from the same resolved numbers) are written once at root level; `<col>` elements (in every region's table) and pinned cells reference them; the tables' own `width` is the exact total. A resize drag re-renders the header and one memoized style object — `DataRow` is `React.memo`ed and untouched. Its memo token does include column-definition identity and editing behavior, so a same-id renderer/meta replacement invalidates cells without making column sizing volatile. The commit handlers are in it by **presence only**: what a row's cells read from them is whether the live mode has one at all (it is part of `canEditCell`), while the write itself goes through the controllers, whose event callbacks always reach the latest one. Taking their identity instead would hand every row a new token on every render of any application that writes its handler inline, which is how one is normally written — nothing in the body would be memoized at all. The corollary is a rule for anything added here: a row may not capture an application callback at render time, because it is no longer guaranteed to re-render when one changes. Column ids pass through `cssSafeColumnId` before becoming variable names, and each geometry family has a disjoint prefix. Three engine invariants:

- **Author sizing is read from the raw-definition registry** (`rawColumnSizing` in `build-columns.tsx`), never from `column.columnDef` — TanStack merges `size: 150, minSize: 20` defaults into every resolved definition, which makes "the author declared no size" unrepresentable after the merge. The registry keys off the per-leaf meta clone created during preprocessing.
- **Display order is pinned-aware everywhere**: header groups and `row.getVisibleCells()` render pinned columns first, but `getVisibleLeafColumns()` ignores pinning — the colgroup, the width specs, and the offset sums all use the `left + center + right` concatenation, or a mid-table pinned column drifts onto its neighbor's `<col>`.
- **A resize handler carries its whole render with it.** TanStack's own resize handler snapshots `getSize()`, which is wrong for grow columns, so `use-column-resize.ts` owns the whole pointer session — and it asks the table for *nothing* at event time. The column, the width on screen, the constraints, and the `columnSizing` entry Escape restores all arrive as a `ResizerSpec` built by the render that drew the handle (`autosize-column.ts` takes the same spec). A ref in context, a `getColumn` lookup, or an atom read would each hand the pointer a value from whichever render pass ran last. The one thing the session re-reads is whether its handle is still on screen, resolved by column id **within the table that started the drag** — a captured node is replaced whenever the header re-renders, which a live drag does on every move, and a document-wide lookup would be answered by another table that happens to have a column of the same id. A column that really leaves mid-drag ends the session instead of writing widths for something that is gone. Rows are unaffected throughout: their geometry is CSS variables, and `DataRow` is memoized.

**The Styles API is revised, never mirrored.** Mantine's `useStyles` re-resolves theme, `classNames`, `styles`, `vars`, `attributes` and the props those read on every render, and hands back a **new getter each time**. Both obvious things to do with it are wrong: put that getter in the context and the context value churns every render, so nothing in the body stays memoized; pin it behind a ref and the identity holds but the answers freeze — a real `styles.row` change never reaches a memoized row — while the ref write itself is a render-phase write a discarded transition can poison.

So `use-styles-revision.ts` compares what the getter *resolves*. Every selector's `className`, `style` and attributes are read once per render (a constant ~25 selectors — per render, never per row) and compared with the last committed answers **structurally, never as text**: own keys by identity, and one level deeper for `style`, because Mantine builds a fresh style object each render while `attributes` may carry event handlers and objects that refer to themselves. Identity is the right test for the rest — a replaced handler is a real change — and an object-valued attribute other than `style` therefore counts as one conservatively. The comparison also weighs the provenance the answers do not expose: a per-call `getStyles(selector, { style })` merges that style through `resolveStyle(style, theme)`, and the class-name shape depends on Mantine's prefix / static-classes / headless / styles-transform context. Same answers and same provenance, and the committed getter is returned — the context value keeps its identity and nothing below re-renders. Anything different, and *this* render's getter becomes the context value, which is a context change and therefore reaches even a `React.memo`ed row. The new answers are committed in an insertion effect, so a render React discards never gets to say what the tree on screen is styled with.

**Row backgrounds flow through one pipeline — painted on cells, never on `<tr>`.** Stripe (parity computed from the data index — `:nth-of-type` would count spacer rows), hover, and selected each set `--ledger-row-bg` on the row; the paint site is `.ledger-row > td`, and pinned cells read `--ledger-pinned-bg`, which follows it. The classic "pinned column doesn't cover stripes/hover" defect is unrepresentable. The cell-level paint is load-bearing: Mantine ships an **unlayered** `tr { background-color: transparent }`, and unlayered author styles defeat anything in `@layer ledger` regardless of specificity — a row-level paint silently loses under the default (unlayered) Mantine stylesheet. Keep any new row tint inside this pipeline, and never paint a property on an element the host styles unlayered. Corollary for pure-behavior elements: don't reach for a host component whose unlayered defaults fight inheritance — the sort control is a native `<button>` reset inside the layer (author rules always beat UA styles), because Mantine's `UnstyledButton` ships an unlayered `font-size` that overrode the layered `font: inherit` on header labels.

**Display rows.** `buildDisplayRows` interleaves data rows and expanded detail-panel rows inside each top/center/bottom zone. The virtualizer counts the center list, while pinned lists remain mounted and use the same one-row-per-item measurement model. Virtualization renders top/bottom spacer `<tr>`s (geometry only, `data-ledger-spacer`) around the window — never absolute positioning, so the real-`<table>` guarantee holds. ARIA indexes concatenate header, all three body sequences, loader, and footer into one logical table even when the center DOM is windowed.

**Pinned rows measure, never assume.** Sticky offsets are the measured cumulative heights of preceding pinned data/detail items, ResizeObserver-tracked (`use-pinned-row-offsets.ts`); callback refs rebind observation when same-count rows are replaced or reordered. How many items each end holds is mirrored in a **layout effect**, and the measurement works from that mirror rather than from the props — the element arrays are refs, shared with a work-in-progress tree, so a transition that renders fewer pinned rows and is then discarded would otherwise drop a row that is still on screen out of every later measurement, with nothing left to put it back (its ref never changes, so its callback never runs again). For the same reason a ref callback writes its element whatever the array's current length is: a row that grows the list attaches during the commit that carries the new count, before the effect that records it has run. The header lives outside the scroller, so top offsets start at 0. A shared `top` stacks every pinned row onto one edge — found by the interactive browser pass; jsdom cannot express it.

**Editing sessions live in the controller layer, not in the editors.** One module each — `use-cell-editing.ts`, `use-row-editing.ts`, `use-instant-editing.ts` — and `useDataTable` only assembles them: each takes the committed snapshot and its slice, and returns a stable surface `meta.ledger.editing` composes. A mounted editor is a *view* of one plus a keyboard surface. This is not tidiness — an editor is unmountable at any moment (virtual scrolling, a hidden column, StrictMode's simulated unmount) while the session is not, and every previous defect in this area came from a session fact living somewhere a scroll could delete. The session owns: the pending draft, what the session has already written, the in-flight commit and its ownership, the pending flag, the error, whether the gate was lost, and whether the session has settled. The editor owns only what is genuinely per-instance: its DOM node, focus, and its own unmount.

An instant column is the same rule with no session in it: a change *is* the commit, so there is nothing to open or close, but the write still out, its failure and the value the application now holds all outlive the control, and any number of cells can hold them at once. So that controller is addressed by *target* rather than by session — nested by row and then column, never a joined key, because row and column ids are opaque application strings and any separator is one an id may contain.

Eight invariants hold this together. Breaking any one of them reintroduces a defect the suite already pins:

- **The slice is a request, not a fact.** `editingCell` / `editingRowId` are controlled, so `start`, `stop`, and every trigger only *ask*. Session boundaries are committed in a layout effect against what actually rendered — never in the render phase, which React may throw away — and an application that declines to move the prop keeps a live session on the row or cell it named. A boundary ends the session **whole**: token, in-flight ownership, pending flag, drafts, error and armed unmount together, whether it comes from a render that moved the slice or from an explicit restart on the target already named. Anything a boundary leaves behind goes on speaking for the session that replaced it — a pending flag most visibly, since the write it belonged to settles into a token that no longer matches and so never clears it.
- **What an editor shows comes from the session, never from a copy taken at mount.** `read(rowId, columnId, source)` answers with the pending value if there is one, else what the session has written, else the cell's own. A remounted editor therefore shows what the row holds, and two editors for the same cell cannot disagree.
- **A session remembers its own writes, until the data moves.** A successful commit takes back the drafts it carried and records them against the value the data read at the time. Once the data moves past that — the write applied, normalized, or another writer's edit — the record retires *permanently*, so data returning to what the write departed from cannot resurrect it.
- **`previousValues` is what the application last knew**, which is that record while it stands and the data once it moves. A column whose definition disappears falls back to the last effective previous the session observed for it, recorded every time the session sees the column — that same record is what tells a gate closing on a column this session was editing apart from a breakpoint taking the column away.
- **Only the settlement that still speaks for the session may act on it.** Requests carry a session token; a settled request whose session has ended reports failure and touches nothing. A commit that lands behind a value typed since keeps the editor open and reports that it is not safe to leave. A commit whose gate shut reports the same, because a cancelled session did not finish.
- **Two gates, and the render owns one of them.** An editor host reaches the screen only if the cell may be edited *now* — `canEditCell`, the current eligibility predicate: the table switch, the live mode's commit handler, the column's `meta.edit`, and the application's own `edit.enabled(row)` — **and** the session for it is live (`editing.active` / `editing.row.active`, which is what a latched gate loss turns off). Eligibility is evaluated in the render itself, and has to be: ending a lost session is a side effect, so reconciliation is a passive effect that runs after the paint, and a render that deferred the gate to it would paint one frame of live, focusable editor behind a gate the application had just shut. It is also not a question an effect could settle for good — `edit.enabled` is application code and may answer differently with no render in between, which is why the commit re-reads it too. Liveness, in contrast, cannot be asked in the render at all, because the answer is a session fact — hence the controller read, keyed to an epoch. Both editor hosts sit behind both gates, and `data-editing` follows them rather than the slice. A cell-mode instant control is behind eligibility only: a change commits immediately, so it has no session to be live or lost.
- **Losing eligibility latches.** A gate that shuts during a session cancels it, and a gate that reopens before the request settles does not un-cancel it — that is the *next* session's eligibility. Automatic reconciliation is idempotent per session — it runs after every render, and asking once for each would be nagging rather than reconciling. A **command** is never that: an Escape, either spelling of `stopEditing`, or a `startEditing` that has to leave the cancelled session first is always a fresh request, because a controlled owner that ignored the last one still has the editor on screen. So a command that finds the session already reconciled asks again itself; and the commit a command runs re-reads the gate rather than trusting what the session opened on, since `edit.enabled` is application code that can turn false with no render in between.
- **The unmount-commit defers one tick** so a remount of the same cell — StrictMode's simulated unmount, or the virtualizer re-mounting a row still in view — cancels it; only a real departure commits, and once unmounted any failure degrades to discard because there is nowhere left to report it. Do not "simplify" this into a synchronous unmount commit; StrictMode self-destructs the editor.

**`isDev` counts a missing `process` as development** (`env.ts`). Vite dev serves library sources to the browser, where `process` does not exist — that is precisely where the guards must fire; production app builds always define `NODE_ENV`. `env.ts` stays dependency-free so its test can stub `process` without re-evaluating React. `warnOnce` keys the once-per-session dev warnings ([state.md](state.md#dev-mode-guard-rails)).

**Infinite loading and layout races.** `onEndReached`'s probe and the unconstrained-virtualization warning both run one `requestAnimationFrame` after commit and ignore unlaid-out viewports (`clientHeight === 0`) — the pre-layout frame reads as "at the bottom" and used to fire phantom loads.

**Popover-nested comboboxes never portal.** Inside the filter popover, `Select`/`MultiSelect` render with `comboboxProps={{ withinPortal: false }}` — a body-level portal reads as an outside click and closes the popover mid-pick.

## Testing strategy

Vitest 4 + jsdom + Testing Library; specs colocated as `<name>.test.{ts,tsx}`; component wrappers render under **`StrictMode`** (its simulated unmounts caught a live editor bug that plain jsdom tests missed). Behavior tests drive the public API — sorting cycles, slice contracts, selection semantics, editing commit/cancel/validate, merge-order warnings — plus regression tests for every browser-found bug jsdom can express (strict `ledger-one-of` matching, the popover-stays-open flow, the deferred unmount-commit, the zero-height `onEndReached` guard, `isDev` without `process`).

What jsdom cannot express — real geometry (pinned-row stacking, scroll windows, adaptive resize, edge shadows) — is verified interactively in the playground with a real browser. When touching those areas, run the relevant playground demo and scroll/drag it. **Dragging is in that category**: dnd-kit's pointer sensor needs layout, so the columns panel's specs drive everything *but* the drag (its bare shape needs no popover to open first) and the pure order math lives in `column-order.test.ts`; the drag itself belongs to the browser pass.

Gates (all must stay green): `pnpm test`, `pnpm typecheck`, `pnpm lint:check`, `pnpm lint:css:check` (mechanical kebab-case enforcement), `pnpm build`, `pnpm check:package` (publint + attw on the packed output; `.attw.json` excludes the typeless `styles.css` entrypoint and pins the `node16` profile). Tests run against TS source via the `source` export condition — a green suite does not prove the build; the last two gates do.
